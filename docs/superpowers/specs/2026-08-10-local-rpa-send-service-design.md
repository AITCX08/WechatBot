# 本地微信 RPA 文本发送服务：设计

**日期：** 2026-08-10
**状态：** 已获用户批准，待实施计划评审

## 目标

在现有 `wx.send.SendBackend` 的 Windows UI Automation 能力之上，提供一个仅监听本机的 HTTP 文本发送接口。该接口向已经登录的 PC 微信发送单条文本消息，并返回可追踪的执行结果。

本实现是自建、可审计的 UI Automation 服务，不依赖 iLink Bot、逆向个人微信协议、内存注入，或第三方闭源 RPA 可执行文件。

## 范围

第一阶段仅包含：

- 监听 `127.0.0.1` 的本地 HTTP 服务；
- `POST /api/chat/send_message` 文本发送接口；
- 本地 API 密钥校验；
- 显式收件人白名单；
- 单消费者发送队列、节流和请求 ID；
- 基于现有 `SendBackend` 的微信窗口附着与文本发送；
- 结构化审计日志（不记录消息正文）；
- 单元测试和一次由用户明确授权的“文件传输助手”真机验证。

## 非目标

第一阶段不包含：

- 群发、朋友圈、自动加好友、自动回复、联系人同步、附件或语音；
- 自动启动、杀死或重启微信；
- 调用任何微信私有网络协议、Hook、内存注入或调试端口；
- 暴露局域网/公网接口；
- 保存完整消息正文、微信聊天记录或第三方服务凭据。

## 架构

```text
调用方
  |  HTTP + X-API-Key
  v
LocalRpaServer (127.0.0.1)
  |-- 请求校验：密钥、JSON、文本长度、收件人白名单
  |-- SendJobQueue：请求 ID、单消费者、去重、状态
  `-- SendBackend：附着已登录微信、定位会话、粘贴并发送
                                      |
                                      v
                               Weixin 4.1 桌面客户端
```

服务直接复用现有 `SendBackend`，不复制其 UIA 逻辑。发送队列全局串行，避免搜索框、剪贴板和微信输入框被并发请求竞争。

## 接口

### `POST /api/chat/send_message`

请求头：

- `X-API-Key`：与本地配置匹配的随机密钥；
- `Content-Type: application/json`。

请求体：

```json
{
  "request_id": "调用方生成的可选幂等标识",
  "recipient": "允许的 wxid 或内置 filehelper",
  "text": "要发送的文本"
}
```

成功接受任务返回 `202 Accepted`，响应含 `request_id` 和 `status: "queued"`。输入无效、密钥无效或收件人不在白名单时返回 4xx。微信未运行、无法附着、无法解析收件人或 UIA 发送失败时，任务标为 `failed`，并返回可诊断的错误类别。

### `GET /health`

只返回服务是否运行、微信是否已附着、队列长度和最近任务状态；不返回联系人、消息正文或密钥。

## 安全与发送保护

- 仅绑定回环地址 `127.0.0.1`；
- API 密钥从项目内运行配置读取，不写入日志；
- 白名单以 wxid 为准；`filehelper` 是唯一默认允许目标；
- 文本设置合理最大长度并拒绝空白内容；
- 请求 ID 在短时间窗口内去重，避免网络重试导致重复发送；
- 日志仅记录时间、请求 ID、收件人标识、结果和错误类别；
- 不提供批量接口，且使用现有的发送节流。

## UI Automation 可靠性

发送前必须确认微信桌面客户端已登录且窗口可附着。当前 `SendBackend` 用搜索并按 Enter 打开会话，存在重复昵称/前缀匹配选错会话的已知风险。因此第一阶段真机验证仅允许 `filehelper`；将来扩展其他收件人前，必须先实现并验证“已打开会话标题与预期收件人一致”的失败关闭校验。

## 测试与验收

单元测试覆盖：

- 回环绑定和 API 密钥拒绝逻辑；
- JSON、文本长度和白名单校验；
- 队列串行化、去重和状态转换；
- `SendBackend` 成功、失败和微信未附着时的映射；
- 审计日志不含消息正文或 API 密钥。

真机验证前提是用户明确指定测试时机。验证仅向“文件传输助手”发送一条明确标记为测试的文本，并检查 HTTP 返回状态及本地审计记录。验证期间不重启微信，也不向其他联系人发送内容。
