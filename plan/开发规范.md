# WechatBot 开发规范

> 本项目开发铁律。新增模块 / 功能都必须遵守。
> 与全局 `~/.claude/CLAUDE.md` 工作流宪章叠加生效。

## 1. 分层与依赖方向

三层，依赖只能自上而下：

- `wx/` — 微信交互层（收/发/联系人），**不掺业务**
- `router/` — 业务路由层（分发/模板/下单/命令/通知/报告/价格）
- `dashboard/` — Web 看板 + 账号生命周期

跨层解耦：`router` 调 `dashboard` 用「惰性 import + 宽 except」，dashboard 未初始化时降级为 no-op。
换底层（sidecar / UIA / 付费 SDK）→ 只动 `wx/` 适配层，业务层零改。

## 2. 微信交互层契约（核心）

- `wx/` 对上只暴露 `WxAdapter`，形状对齐 `wcferry.Wcf` 的子集
- 只实现 robot.py 实际用到的接口，不复刻全部 39 个（YAGNI）
- 底层换实现只改 `wx/receive.py`（收）或 `wx/send.py`（发），不动 facade 契约

## 3. 能力获取：P0 / P1 / P2（先找现成，禁止从零手搓）

新能力需求，按优先级找现成的：

- **P0** — 先搜现成 skill / 工具
- **P1** — 再找成熟开源（本项目 receive 用 `wechat-decrypt`、send 用 `uiautomation`，都是 P1）
- **P2** — 实在没有才手写，且 commit / 存档里要写清「为什么 P0/P1 都不行」

> 本项目本身就是 P0/P1 纪律的产物：没手搓微信 4.x hook，而是 wechat-decrypt（收）+ uiautomation（发）
> 组合。动手前先做一轮 GitHub 全网搜索是默认动作。

## 4. 配置 / 数据 / 契约

### 配置 / 数据 / 密钥分离
- 配置模板 `config.yaml.template` 入 git；实际 `config.yaml` 走 gitignore（含密钥）
- 运行时数据 `data/`（如 `runtime_accounts.json`）、`logs/`、`wx/decrypted/` 全 gitignore
- 路径走 `pathlib`，不写死盘符

### 审计事件格式 = 单一真相源（single source of truth）
- `logs/audit/orders-{account}.jsonl` 的事件 shape 是一份**隐形契约**：
  `order.py` 写、`reporter.py` / `notifier.py` / dashboard 读。
- 事件字段：`event` / `ts` / `draft{platform,kcname,requester_wxid,...}` / `result` / `error`
- **改这个 shape 必须同步检查全部读方**，否则报告/通知会静默算错而不报错
- 后续若收成 `router/` 下一个 dataclass，则以该 dataclass 为唯一定义处，读写都走它

## 5. 代码规范

- 遵循 PEP 8；用类型注解（大量 `from __future__ import annotations`）
- 类与公开函数必须有 docstring
- 关键技术决策写明「为什么选 A 不选 B」
- 单文件单一职责；文件过大 = 「做太多」的信号

## 6. 测试规范（TDD 强制）

- 先写失败测试 → 跑确认 RED → 写实现 → 跑确认 GREEN → 提交
- 覆盖率目标 ≥ 80%；核心功能必须有测试
- 提交前必须通过全部测试（当前 191 个）
- UIA / sidecar 需真实环境的能力，单测只覆盖纯逻辑；真实联调用 `scripts/smoke_*.py`
- CI：每次 push/PR 在 GitHub Actions windows-latest × Python 3.10/3.11/3.12 跑全套

## 7. Git 提交规范

格式 `<type>(<scope>): <subject>`：
- type：`feat` / `fix` / `docs` / `refactor` / `test` / `chore`
- scope：`wx` / `router` / `dashboard` / `config` / `robot` / `main`
- footer 署名：`Co-Authored-By: Claude Opus 4.7 (1M context) <noreply@anthropic.com>`

## 9. 存档（详见 plan/README.md）

每次开发 / 修复 / 大模块操作完成 → 在 `plan/<类别>/` 留一份 `YYYY-MM-DD-<简述>.md`（5 段式）。
代码变更同步更新 `CHANGELOG.md`。

## 10. 大文件分批写

大文档分批写（`Write` 首块 → `Edit` 逐节追加），避免一次性超大 payload 触发 socket 断连。
